# 学祭の会計画面を使いやすくするための一次資料調査

調査日：2026-10-30。前提はPC1台、マウスとキーボード、会計担当1人。商品を渡すときに番号札もほぼ同時に回収する。

`src/components/Checkout.tsx`、`Waiting.tsx`、`History.tsx`、`DataPanel.tsx`、`Help.tsx`、`src/App.tsx`、`src/styles.css`を読んだ時点の改善候補。以下の「根拠」は一次資料の要約、「適用」はこの運用に対する設計判断である。資料だけで改善効果は証明できず、リアルユーザーテストは未実施。WCAG全体への適合監査も行っていない。

## 1. 普段の受け渡しを一つの操作にする（優先度：高）

- **根拠：** NN/gは現実の言葉・順序に合わせること、見て分かる選択肢により記憶の負担を減らすことを挙げる。[NN/g：ヒューリスティクス2・6](https://www.nngroup.com/articles/ten-usability-heuristics/)
- **現コードの候補：** `Waiting.tsx`は「商品を渡した」「札を回収した」を毎回別々に押す。通常運用では同じ出来事を2回記録するため、片方だけ押して札の回収待ちが残りやすい。
- **適用：** 札番号・商品・本数の近くに「商品を渡して札を回収」を主操作として置く。札を受け取れない例外は「商品だけ渡す」として補助操作へ。内部では受け渡しと回収の事実を区別し、両方の完了まで札を再利用しない制約を保つ。これは両方の事実を確認して実行する操作であり、回収を自動的に推測する仕様にはしない。
- **確認：** 通常の受け渡し1件を1クリックで終えられるか。未回収例でも商品だけ渡せるか。次の注文の入力中に操作しても本数が消えず、札の空きが実物と一致するか。

## 2. 次の判断に要らない情報を下げる（優先度：高）

- **根拠：** NN/gは不要な情報が必要な情報と競合すると説明する。GOV.UKは通知の多用を避け、現在の作業に関係する情報は本文に置く。[NN/g：ヒューリスティクス8](https://www.nngroup.com/articles/ten-usability-heuristics/)、[GOV.UK：Notification banner](https://design-system.service.gov.uk/components/notification-banner/)
- **現コードの候補：** `History.tsx`は当日範囲でも各行に日付、価格名、セット数を繰り返す。売上・本数・会計件数を同程度の強さで並べる。会計画面にも開催名・営業日・保存件数が常時出る。
- **適用：** 会計中は商品、本数、請求額、お釣り、札、未受け渡しを優先する。履歴では売上を主にし、販売本数・会計件数は小さな内訳にする。当日の日付は範囲見出しで示し、全期間表示では日別に区切るなど注文の区別に必要な日付を残す。価格情報は価格差の確認時にだけ展開する。復旧・再開時の開催日確認は残す。
- **確認：** 「今いくら受け取るか」「札何番を渡すか」「この会計を返金したい」を説明なしで探してもらう。削減後も前日の注文を今日の注文と取り違えないか確認する。

## 3. 保存確認後に結果と次の動作を短く示す（優先度：高）

- **根拠：** NN/gは操作結果を速やかに伝えることを求める。WCAG 4.1.3はフォーカスを移さない状態メッセージを支援技術が認識できるようにする。[NN/g：ヒューリスティクス1](https://www.nngroup.com/articles/ten-usability-heuristics/)、[W3C：Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **現コードの候補：** 会計確定後は支払い欄が新規注文へ戻り、右の待ち一覧に追加される。`App.tsx`の保存件数だけでは、どの札の会計が終わったか、次に札を渡してよいかが分かりにくい。
- **適用：** 保存結果を確認してから「札 12　会計済み」「番号札を渡してください」のように表示する。完了音や常時バナーを増やさず、会計欄の近くに短い結果を残す。支払い金額の入力や次の注文を奪うダイアログにしない。状態文には`role="status"`などを使う。保存結果が不明なら成功表示を出さず、既存の復旧手順へつなぐ。
- **確認：** 通常確定・保存中・保存失敗を見分けられるか。完了表示の札と注文が一致するか。連続会計で前の完了が次の会計の結果に見えないか。スクリーンリーダーでも結果文が通知されるか。

## 4. 入力間違いをその場で直し、金銭操作の保護を残す（優先度：高）

- **根拠：** NN/gは影響の大きい誤りの予防と明確な復帰手段を重視する。GOV.UKは入力エラーで原因・修正方法を示し、入力済みの値を消さないよう求める。[NN/g：ヒューリスティクス3・5](https://www.nngroup.com/articles/ten-usability-heuristics/)、[GOV.UK：Error message](https://design-system.service.gov.uk/components/error-message/)
- **現コードの候補：** `Checkout.tsx`は不足する預かり金額でボタンを無効にするが、その近くに不足の理由がない。数量の範囲外入力は受け付けず元の値が残る。預かり額をお釣り表示後に修正できる点、返金前の準備保存は既にある。
- **適用：** 入力した額が不足する間だけ「あと300円必要です」のような短い説明を金額欄の近くに表示する。入力自体を消さず、修正できるようにする。返金時は札・注文内容・返金額を同時に見せる。通常の本数変更には確認を増やさず、返金・復元・再開時の現金確認は残す。
- **確認：** 空欄、不足額、負数、小数、桁の大きい数から迷わず修正できるか。支払い準備後の額の修正・再開で現金を二度受け取らないか。返金対象が別の注文に変わらないか。

## 5. 大きなクリック領域を維持する（優先度：中）

- **根拠：** WCAG 2.2の2.5.8は原則24×24 CSS px以上、または所定の間隔等を求める。これは最低条件であり、より大きい領域は押しやすさに役立つ。[W3C：Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- **現コード：** `styles.css`には共通ボタンの高さ44px、数量ボタン50×50px（狭いPC幅では45×48px）がある。既に良い点であり、タッチ端末向けの不足と断定しない。一方で受け渡しボタンの文字は11〜12pxになる。
- **適用：** 通常操作の高さ44px前後を維持し、札番号を見てその近くで押せる配置にする。文字が収まらない場合は領域を削らず文言や並べ方を変える。チェックボックスは説明ラベル全体もクリックできる現在の構造を維持する。
- **確認：** 本番PCの画面幅で実際のクリック領域を測る。狙った数量増減・受け渡しが隣の操作と誤って押されないか、長い札番号や折り返しでも確認する。

## 6. キーボード操作とフォーカスを途切れさせない（優先度：中）

- **根拠：** WCAG 2.1.1はキーボードから同等の操作ができること、2.4.7はフォーカス位置を見えるようにすることを求める。[W3C：Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)、[W3C：Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html)
- **現コード：** ネイティブの`button`、`input`、`dialog`を使い、`styles.css`に`focus-visible`がある。預かり欄の`autoFocus`もある。一方、会計確定でその欄が消えた後のフォーカス位置は明示されていない。
- **適用：** 独自ショートカットを先に増やさず、Tab・Shift+Tab・Enter・Space・Escapeで進める標準操作を整える。画面の切り替えや会計終了で要素が消える場合、次の注文の入力位置など適切な場所へ戻す。金銭確定を自動実行しない。
- **確認：** マウスを置き、注文入力から会計確定、次の注文、履歴の返金、使い方の開閉まで通す。現在位置が常に見え、閉じたダイアログの起点へ戻れるか。長い待ち一覧でも現在のフォーカスが画面外に隠れないか。

## 7. 読める文字と現場の言葉を使う（優先度：高）

- **根拠：** WCAG 1.4.3は通常文字に4.5:1以上、大きな文字に3:1以上のコントラストを求める。NN/gは内部用語ではなく利用者の言葉を使うことを挙げる。[W3C：Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[NN/g：ヒューリスティクス2](https://www.nngroup.com/articles/ten-usability-heuristics/)
- **現コードの候補：** 本文の基準は15pxだが履歴・説明・受け渡しボタンには10〜12pxが多い。見出しや主要数値で`font-weight: 850`が使われる。`DataPanel.tsx`は既に「バックアップを保存」「売上一覧を出力」と書き、形式名をボタンに出していない。
- **適用：** 日本語の潰れを避けたいという依頼に合わせ、通常文字は400〜500、見出しや商品名は600〜700を候補として実画面で比較する。金額・本数は大きさと余白で強調し、全要素を太くしない。主要な操作名・注文内容は14〜16px程度から確認する。これらの字号・字重は今回の設計案であり、WCAGが一律に指定する数値ではない。「札」「お預かり」「お釣り」などの用語を揃え、内部ID・JSON/CSVを通常操作の判断に要求しない。
- **確認：** 実際の日本語フォントで「札回収」「全額返金」「会計済み」の字形を見比べる。通常・選択中・ホバー・エラーの文字色と背景色を測る。200%拡大でも商品、金額、ボタン文言が欠けないか。名前だけで保存目的が区別できるか。

## 実利用者による最小限の確認（今後）

本番の会計担当者に、説明を先に暗記してもらわず、次の場面を操作してもらう。時間短縮の数値は現時点で主張しない。

1. もも2本・かわ1本を注文し、1,000円で会計。お釣りと渡す札を口頭で確認する。
2. 次の注文を入力中に先の札の商品を渡して回収し、入力内容が残ることを確かめる。
3. 商品だけ渡して札を回収できない例外を記録し、その後札を回収する。
4. 預かり額を間違えて修正する。履歴から指定した注文を見つけて返金する。
5. 会計途中から再開し、現金の再受領を避けて記録を確認する。

観察するのは、手が止まった箇所、文言の読み違い、別の札を選んだ回数、助けを求めた箇所。実施結果と改善後の再確認を別に記録する。

## 実装への反映（2026-10-30）

- 専門語を画面から外し、必要な確認を操作時に示すようにした。
- 極太字と均等な集計カード、履歴の内部ID・日付の重複を削減した。
- 通常の受け渡しと札回収を1回の操作にした。ユーザーの最終指示で、個別に記録するメニューは画面から外した。
- 保存が成功する前には完了を表示しない。正常な保存中だけ現れる確認待ち欄を抑止し、既存の未解決記録は再試行中も維持する。
- 戻す画面はダイアログに分け、入力内容・元の画面の位置・フォーカスを維持する。エラーもダイアログ内に表示する。
- 基本色を紙色・墨色・黄色に限定し、赤は注意が必要な操作に使用する。画像の色は別扱いとする。
- 標準ボタンと入力欄は40pxに揃え、札は小さなバッジ、完了は名前付きのチェックアイコンとした。40pxは今回の設計値でありWCAGの規定値ではない。
