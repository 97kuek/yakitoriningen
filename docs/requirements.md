# 焼き鳥人間 会計システム 要件定義書

作成日：2026-10-27

更新日：2026-10-30

状態：第5稿。誰のPCでもブラウザから気軽に起動できることを優先し、PWA＋IndexedDBを採用方針とする。保存・復旧の受入条件は維持し、実機検証はこれから行う。

DBへの記録の確実性を最優先とし、PCの処理速度は評価対象から外す。OS別の保存用プログラムの導入は求めず、ブラウザ内DBのトランザクション・結果照合・業務ログ・バックアップを実装して検証する。

## 1. 目的

WASAが早稲田祭に出店する焼き鳥屋「焼き鳥人間」で、注文受付・現金会計・注文確認・商品受け渡しの滞りを減らし、多くのお客さんに対応できるようにする。

開発者が当日現場にいなくても担当者が使え、翌年以降の出店にも引き継げるシステムを目指す。

## 2. 前提と制約

| 項目 | 内容 |
|---|---|
| 開催 | 早稲田祭の2日間。16:00が終了1時間前という説明。開始時刻と各日の営業時間は確認待ち |
| 出店場所 | 屋外。携帯回線の混雑や通信断があっても営業できる構成を目指す |
| 利用端末 | PC1台で完結。会計担当1人が主に操作する。OS・機種・ブラウザは未定 |
| 利用方法 | 公開URLから準備するPWA。対応ブラウザのあるPCで使い、別の保存用プログラムは導入しない |
| 営業中の通信 | 注文入力・会計・保存・注文確認・集計にインターネットを必要としない |
| 初回準備 | 使用するPCごとに営業前にオンラインでアプリを取得し、オフライン起動とDB保存を確認する |
| 現場の技術対応 | 開発者の立ち会い、Docker、コマンド操作、OS別の起動アプリを前提にしない |
| 費用 | 有料サービスを避ける。営業中の処理は端末内で完結させる |
| 過去の実績 | 出店経験はあるが、注文件数などの過去データはない |
| 規模 | 会計と受け渡しの2人体制を想定。注文件数、販売予定本数、ピーク時の注文量は確認待ち |

本書では「確認済み」を会話で示された要望・合意事項、「提案」を今後確認する仕様候補として扱う。初期版は別のスマホへの注文送信やクラウド同期を行わず、同じPCで注文を確認する構成に変更する。

### 2.1 販売商品と初期の価格候補

| 項目 | 担当者からの回答 |
|---|---|
| 商品 | もも・かわ・ねぎま |
| 通常の単価 | 1本150円 |
| セット | 5本600円 |
| 値下げ | 16:00ごろを目安に1本50円。実施タイミングは混み具合などに応じて変更する |

これらは初期設定に用いる価格候補とし、プログラム内の固定値だけで運用しない。価格・セットの適用条件は画面から選択変更できるようにする。種類の混在や自動セット適用を一つの方式に固定しない。

設定できる範囲の設計提案は、単品単価、セット本数・価格、セット自動適用の有効・無効、種類混在の可否、価格プリセットの選択とする。値下げは現場で手動切り替えできるようにする。詳細は[アーキテクチャ設計書](architecture.md)に記載する。

## 3. 利用者と画面

| 利用者 | 役割 |
|---|---|
| 会計担当 | PCで商品・数量を入力し、合計・お釣りを確認して会計を確定する |
| 受け渡し担当 | 同じPCの注文番号・種類別本数を確認し、商品を渡す。完了操作を誰が行うかは確認待ち |
| 設定・集計を行う担当 | 価格変更、売上・費用の確認、データ出力を行う。会計担当との兼任を想定し、詳細は確認する |

会計入力と未受け渡し注文を同じ画面で確認できる構成を提案する。集計・履歴・設定は別の表示へ切り替える。受け渡し側の注文確認のために、会計入力を中断する必要がない配置を検討する。

## 4. 業務フロー

1. 営業前に開催回・営業日・適用価格・番号札・保存状態を確認する。
2. お客さんが会計担当に注文を伝える。
3. 会計担当がもも・かわ・ねぎまの個数を入力し、適用中の価格ルールと合計を確認する。
4. 現金を受け取る前に空き番号札を確認・仮確保し、注文ID・数量・提示価格を保留記録としてDBへ保存する。満札なら通常の入金操作へ進ませない。
5. お預かり金額とお釣りを確認し、入金と釣り銭のやりとり後に会計を確定する。
6. 端末内DBへの保存成功後、注文番号・種類別本数を未受け渡し一覧に反映し、番号札を渡す。
7. 商品を渡し、番号札の回収と受け渡し完了を確認する。
8. 休憩時や閉店時にバックアップを出力する。実施タイミングと保存先は本番前に決める。

上記の入金前の保留保存は、再起動後にも照合できるようにするための設計提案とする。保留保存だけで売上には計上しない。保存結果が不明な場合は、同じ注文ID・操作IDでDBを照会してから再試行し、別注文への再入力や再入金を促さない。

番号札は1〜20程度を担当者からの初期案とし、番号の範囲は設定可能にする提案とする。満札時の受付、紛失時、部分的な受け渡し、取消・返金時の手順は確認待ち。商品を渡したことと、実物の札が回収され再利用可能になったことは分けて記録する。

| FR-02 | 合計金額 | 選択した価格ルールで合計を計算する。単価・セット価格・適用条件を変更できる | 可変式にする要望は確認済み。設定項目の詳細は設計提案 |

| FR-04 | 会計確定・保存 | 入金確認後、端末内DBへ注文を保存する。連打による二重登録を防ぐ | 会計・ローカル完結は確認済み。保存方法の詳細は設計提案 |
| FR-05 | 同一PCでの注文確認 | 会計済み注文を同じPCの未受け渡し一覧へ反映する | PC1台の方針に合わせて従来の別端末共有から変更 |

| FR-09 | 商品・価格設定 | 商品や価格設定を画面から変更し、次回出店でも再利用できる | 価格を選択変更する方針は確認済み。商品編集の範囲は設計提案 |
| FR-10 | 注文履歴・売上集計 | 合計販売本数と実際の売上金額を端末内の注文から集計する。履歴を確認できる | 本数・売上は確認済み。集計の期間と取消・返金の扱いは確認待ち |
| FR-11 | 操作の保護 | 価格変更・取消・データ復元などを通常の会計操作と分け、確認操作を設ける | 設計提案。従来のオンライン認証要件は取り下げる |
| FR-12 | 開催回・営業日 | 次回出店と過去の会計記録を分け、営業日ごとにも確認できるようにする | 設計提案 |
| FR-13 | バックアップ・復元 | ネットなしでJSON形式のバックアップを出力・復元できる。集計用CSVも出力する | ローカル運用の設計提案。保存先と実施手順は確認待ち |
| FR-14 | 値下げの切り替え | 通常・値下げなどの価格プリセットを手動で選べる。価格や適用条件も変更できる | 可変式にする方針は確認済み。操作の詳細は設計提案 |
| FR-15 | 利益の表示 | 開催回全体の売上（返金差引後）から登録した経費合計を差し引く。未登録と0円を区別する | 開催回全体で経費を登録する方針を確認済み |

「未受け渡し本数」には調理済みの商品も含み得る。これから焼く必要がある本数と区別し、焼き置き・包装・受け渡しの運用を確認して表示を決める。

### 5.1 注文番号と会計記録

再利用する札番号と、一意な注文IDを分ける。札番号が同じでも過去の注文を上書きしない。

注文・札状態・対応する業務ログを同じDBトランザクションで保存する。札の空き確認と割り当ても同じトランザクション内で検証する。札を解放する際は、対象の注文IDと今回の札割り当てIDが現在の所有者に一致することを確認する。

会計・受け渡し・札回収・取消・返金・設定変更は、再起動後も同じ操作IDで照合できるようにする。同じID・同じ内容の再試行には既存結果を返し、同じIDで異なる内容が送られた場合は拒否する。DBのコミットが成功したのに画面へ反映できなかった場合を、保存失敗と区別する。

現金受領後に保存できなかった場合の紙への控え方も運用で決める。紙で営業を続ける場合は、照合用番号、当時の価格・本数、入金・受け渡し状況を保持して復旧入力する手順が必要であり、通常の新規会計として入れ直さない。

### 5.2 価格変更

注文には、商品名・個数・適用した価格設定・金額の内訳・合計を保存する。現在の設定で過去の売上を再計算しない。

設計提案として、数量未入力の空の会計欄は最新の価格設定を使い、最初の商品入力時に価格の版を固定する。設定変更後も入力中の金額は自動変更しない。入力中の注文に変更を適用する場合は旧額・新額を表示し、お預かり金額とお釣りを再確認する。価格設定の変更履歴も同じトランザクションで残す。

### 5.3 集計と費用

販売本数は焼き鳥の本数を合計し、セットも5本なら5本として数える。売上は注文に保存した実際の販売金額を集計する。取消・返金時に売上と本数をどう調整するかは確認待ち。

利益は「開催回全体の売上（返金差引後）− 登録した経費合計」とする。仕入れ・備品などの合計額を登録し、追加費用があれば合計を更新する。経費未登録は0円と区別する。日別・時刻別の売上と種類別販売本数をグラフで確認できる。

セットの一部取消では返金額を単価から自動的に決めない。初期版で部分返金を扱うかを含め、現場の返金ルールを確認する。採用する場合は元の会計を残し、実際の返金額と減らす本数を別々に確認して記録する。累積返金額が元の売上を超えるなどの不整合はDB保存時に拒否する。

## 6. オフライン運用とデータ保全

### 6.1 初回準備と通常営業

使用するPCで営業前に一度オンラインでアプリ本体を読み込み、必要な素材を端末に保存する。初回準備時だけ通信する運用はユーザーに確認済み。通常営業はインターネットを必要としない。ZIPやOS別インストーラーの手動導入は求めない。

外部のフォント、CDN、認証、APIを営業中の必須処理に含めない。アプリの更新は営業終了後にバックアップしてから行い、営業中に強制再読み込みしない。

### 6.2 保存先と制約

注文・設定を使用PCのブラウザ内のIndexedDBに保存する。データはURLのオリジンとブラウザのプロファイルに結び付く。他のPC・ブラウザに自動では移らない。同じブラウザの通常プロファイルを使用し、プライベートモードで営業しない。

永続ストレージの利用を要求し、保存・再起動・オフライン起動を実機で確認する。永続化の要求が承認されることや、端末故障・ブラウザデータ削除からの保護は保証しない。

既存営業の再開時にDBが見つからない場合は、新規の空DBで自動的に営業を再開しない。初回準備と営業再開を分け、開催回・営業日・確定件数・直近の記録・未解決操作を確認する。翌日に日付が変わっても、未完了注文や未回収札を一括初期化しない。

### 6.3 バックアップ

JSONを注文・価格設定・札状態・費用などの復元用、CSVを集計・確認用とする。DB内部にコピーを置くだけの処理をバックアップとは扱わない。

休憩時・営業終了時のファイル出力を候補とし、保存先と頻度は本番前に確定する。PC自体の故障に備えるには、出力済みファイルをUSBメモリなど別の保存先にも移す必要がある。最後のバックアップ以降の記録をすべて復元できるという保証はしない。

復元前に形式・バージョン・注文と札の整合性を検証し、件数などを確認してから反映する。既存データの退避と、誤ったファイルでの上書き防止を設計する。

バックアップは注文・札・設定・ログを同じ時点の状態として取得する。ファイルの生成・ダウンロード開始と、保存先での確認・別媒体への退避を区別する。復元は会計を止めて行い、中断・容量不足後も元の状態か完全な復元状態のどちらかを保持する。復元前の保留操作を自動再実行しない。

ブラウザデータの消去やPC故障で失ってよい記録の範囲、復旧まで紙で営業できるかは未合意。この許容範囲に合う頻度と保存先を決めることを、本番利用の条件とする。

## 7. 非機能要件

| ID | 分類 | 要件・検証方針 |
|---|---|---|
| NFR-01 | 操作性 | 会計と未受け渡し注文を同じPCで確認し、入力・確認・画面切り替えを減らす |
| NFR-02 | 対応環境 | OS別の実行環境を現場で用意せず、対応ブラウザを明示して実機で検証する |
| NFR-03 | 保守性 | 画面、金額計算などの業務処理、保存処理を分離する |
| NFR-04 | 運用性 | 開発者不在で起動・営業前確認・終了確認・バックアップを行える手順を整える |
| NFR-05 | データ整合性 | 連打や二重起動による二重登録・札番号の重複を防ぎ、DB保存成功後に会計の保存完了を表示する |
| NFR-06 | データ保護 | PCとブラウザの利用者を限定し、誤操作の確認と変更記録を設ける。注文・費用・バックアップを公開リポジトリへ入れない |
| NFR-07 | 継続利用 | 開催回・営業日・当時の価格を保持し、設定変更で過去の売上が変わらないようにする |
| NFR-08 | 費用 | 営業中の処理に有料サービスやクラウドDBの使用量枠を必要としない。配布先の無料枠は別途確認する |
| NFR-09 | 業務の継続 | 模擬営業で会計・注文確認・受け渡しが滞らないか確認する。PCの処理速度の優劣は評価対象から外し、DB記録の確実性を優先する |
| NFR-10 | オフライン対応 | 準備済みPCで、通信を切った状態の再読み込み・ブラウザ再起動後も会計と注文確認ができることを検証する |
| NFR-11 | 復旧 | 保存失敗、アプリ更新、PC変更時のバックアップ・復元を検証する |
| NFR-12 | 業務ログ | 会計確定、取消・返金、受け渡し、価格変更を追記型の操作記録としてDBに残す。確定済みの会計を訂正・削除で消さず、関連する調整記録を残す |
| NFR-13 | 保存完了の判定 | 注文・札状態・対応する業務ログを同じトランザクションで記録し、コミット完了前に保存済みと表示しない。データの途中状態と二重保存を防ぐ |
| NFR-14 | 永続性と検証 | 耐久性設定を明示し、検証対象の異常終了・再起動では保存完了済み記録の欠落0を採用基準とする。未試験の条件は未検証とし、停電や媒体故障への無条件の保証はしない |
| NFR-15 | 結果照合 | 保存成功・保存失敗・結果不明を区別し、再起動後も保留中の注文ID・操作IDから照会できる。結果不明のまま別注文として再登録しない |
| NFR-16 | バックアップ・復元の整合性 | 全データを同じ時点の状態として出力する。復元データと新DB世代を原子的に反映し、中断後も元の状態か完全な復元状態を保持する。全更新は期待するDB世代を検証し、復元前の古い操作を拒否する |
| NFR-17 | 状態の制約 | 注文・操作IDの一意性、札の現在の所有者、価格版と金額、調整上限をDB保存時に検証する。画面の操作抑止だけに頼らない |
| NFR-18 | 再開時の保護 | DB消失を空DBへの自動初期化で隠さず、営業日・直近の記録・未解決操作を確認して再開する |

端末の保存機能が使えない場合、保存できたように表示して営業を開始しない。初期版はPC1台・会計操作用の画面1つを基本とし、複数タブからの同時会計は対象外とする。二重起動時の操作抑止に加え、DB側でも競合や古い操作を拒否する。受け渡し操作で入力中の別注文の数量・価格・お預かり金額を消さない。

## 8. 技術方針

| 部分 | 採用方針 |
|---|---|
| 画面・ビルド | React＋TypeScript＋Vite |
| 起動 | 公開URLから事前準備するPWA＋Service Worker |
| DB | IndexedDB＋Dexie.js |
| 業務処理 | ブラウザ内のTypeScript。確定・検証・保存の処理経路を集約 |
| 配布 | Firebase Hostingの無料枠による静的配信を候補とする |
| バックアップ | 同じ時点の状態をJSONへ出力し、保存先・別媒体への退避を確認 |

クラウドDB同期、オンライン認証、Go等の保存用アプリは初期版に含めない。保存・復旧の受入条件を満たすことを本番利用の条件とし、PWAを選んだだけで安全に保存できると判断しない。

詳しい責務分担、価格ルール、保存処理、配布の条件は[アーキテクチャ設計書](architecture.md)を参照。

## 9. 規模と検証

実際の注文件数は未確定。1日1,000件・3,000件などを仮の検証条件とし、販売予定本数などが分かり次第更新する。この数字は販売予測や合意済みの性能要件ではない。

検証の中心は端末内DBの保存・再起動後の保持、注文一覧・集計の応答、設定変更時の金額、番号札の再利用、バックアップ・復元とする。クラウドDBの読み書き回数による営業中の停止は検証対象から外れる。端末の保存容量や保存失敗への対応は別途確認する。

## 10. 確認待ちの事項

| ID | 確認事項 | 影響する設計 |
|---|---|---|
| Q-01 | 価格・セットの設定項目の範囲、初期の混在可否・自動適用設定 | 設定画面と価格ルール。設定可能にする方針は確認済み |
| Q-02 | 本番で使用するPC・ブラウザと、準備完了の確認担当 | PWAの事前準備と実機検証 |
| Q-03 | 営業時間、販売予定本数、ピーク時に焼ける本数、会計・受け渡しの配置 | 模擬営業の条件とPCの設置 |
| Q-04 | 焼き置き、包装、部分的な受け渡し、完了操作を誰が行うか | 注文一覧、完了操作、担当間の連携 |
| Q-05 | 札の番号範囲、回収・再利用、満札・紛失時の対応 | 注文との照合と札の状態 |
| Q-06 | PC故障・保存失敗時の紙への切り替え、バックアップ先と頻度 | 会計記録の保全と復旧 |
| Q-07 | 注文変更、取消、返金、売り切れ時の対応 | 会計記録、変更履歴、状態の遷移 |
| Q-08 | 現金以外の支払い | 支払いの記録方法。外部の決済サービス自体の通信要件は別に扱う |
| Q-09 | 経費に含める実際の費目と集計担当 | 開催回全体の経費合計として登録。日別売上・種類別本数・利益を実装 |
| Q-10 | 現場責任者、バックアップ保管・引き継ぎ担当 | 営業中の判断と翌年への引き継ぎ |
| Q-11 | バックアップを別のPCへ引き継ぐ際の担当と確認方法 | 別PCでの事前準備、データ復元、営業再開の照合 |
| Q-12 | ブラウザデータ消去・PC故障時に許容する記録損失の範囲と、紙営業の可否 | バックアップ頻度・別媒体・復旧手順。本番利用前に合意する |

## 11. 実装・本番運用までの進め方

1. 再設計案を確認し、初期版の機能範囲・設定項目・現場の運用を確定する。
2. 実装計画を作成し、価格計算・DBトランザクション・オフライン起動を先に検証する。
3. 通信なしでの起動、会計、注文確認、集計、ファイル出力と復元を検証する。
4. 価格・セットの切り替え、入力途中の再計算、過去の売上維持、札の再利用、保存失敗、二重起動を確認する。
5. 会計・受け渡し担当で模擬営業を行い、PC1台の配置と操作で注文が滞らないか確認する。
6. 開発者不在で営業前の準備、営業後の確認、バックアップ、復元を行えるか確認する。
