# 要件定義書

本書は「焼き鳥人間」の機能と運用条件を定めます。実装の構成は[全体アーキテクチャ](architecture.md)を参照してください。自動試験と未検証の項目は、本書の受入条件に記載しています。

## 1. 目的と利用条件

WASAの早稲田祭出店で、注文受付・現金会計・注文確認・受け渡しをPC1台で行います。開発者が当日いなくても担当者が操作でき、翌年も引き継げることを目指します。

早稲田祭は年1回、2日間開催します。注文・在庫・経費・バックアップは営業日ごとに管理し、新しい営業を作成しても過去の記録はアプリ内に残します。商品・価格・札枚数は引き継いで編集でき、在庫は日ごとに任意で登録します。年単位で記録を初期化する操作は設けません。

| 項目 | 条件 |
|---|---|
| 利用端末 | PC1台・会計画面1つ。会計と受け渡しの2人体制を想定 |
| 初回準備 | 営業前にオンラインでアプリを取得し、オフライン起動と保存を確認 |
| 営業中 | 注文・会計・保存・受け渡し・集計を通信なしで実行 |
| 起動方法 | ブラウザでURLを開くPWA。現場でコマンドやOS別の保存用アプリを用意しない |
| 保存 | 端末のIndexedDB。クラウドDB同期・オンライン認証は使わない |
| 優先事項 | DB記録の確実性。PCの処理速度の優劣は評価対象外 |
| 配布 | Cloudflare Pagesによる静的配信。公開・更新手順は別文書 |
| 対象外 | 複数PCの同時会計、別スマホへの注文送信、部分返金・部分受け渡し、紙からの復旧入力 |

本番のPC・ブラウザ、営業時間、販売予定本数、担当者と配置は運用前に確定します。

## 2. 商品と価格

- 初期商品はもも・かわ・ねぎま。価格の初期値は通常各150円、値下げ各50円、通常のセットは組合せ自由の5本600円とする。
- 商品は最大30種類。商品ごとにID・名前・通常価格・値下げ価格を持ち、画面から追加・削除・変更できる。
- セットは一つのルールとして対象商品群・本数N・価格X円を設定する。対象商品から組合せ自由でN本を選び、適用可能な組合せのうち最安額を使う。単品より高いセットは適用しない。
- 値下げは担当者が手動で切り替え、全商品にそれぞれの値下げ価格をまとめて適用する。値下げ中のセット適用は別に設定し、既定では無効とする。
- 旧形式の種類別セット設定・価格・バックアップを引き続き読み込める。
- 最初の商品入力で価格の版を固定する。価格や商品を変更しても、入力中・会計済みの注文の商品名・数量・当時の価格・合計を変えない。
- たれ・塩だれの希望は受け渡し時などに口頭で確認し、会計画面では選択・記録しない。

値下げは16:00ごろを目安とする案がありますが、自動切り替えは行いません。実施時刻は現場で判断します。

## 3. 画面と業務フロー

ホームから営業の準備・会計の再開・営業後の集計へ進みます。会計中は数量入力と札回収待ち一覧を並べ、中央のナビゲーションにホーム・会計・注文履歴・設定を配置します。ロゴを押してもホームへ戻れます。集計はホームから開く専用画面とし、会計中のナビゲーションには含めません。

1. 初回は「営業を準備」で営業名・日付・商品・価格・札枚数・任意の在庫を設定する。営業名は日ごとに付け、新しい営業の作成時とホームの鉛筆アイコンから編集する。変更しても過去の注文や他の日の名前を書き換えない。ホームには保存済みの営業名と日付、確認が必要な途中の会計だけを表示し、「会計を始める」で再開する。
2. 商品の本数を入力し、合計とセット内訳を確認する。
3. 「会計へ」で注文と空き札を保留保存する。空き札がなければ現金を受け取らず、札の回収を待つ。
4. お預かり金額と確定操作を保存し、お釣りを確認する。
5. 現金・釣り銭のやりとり後に「会計を確定」で札の確認画面を開く。渡す番号を確認・選択し「この札で確定」で保存する。閉じた場合は未確定のまま戻る。保存成功後、待ち一覧へ反映された札を渡す。
6. 商品を渡して札を回収し、完了操作を一度だけ行う。
7. 休憩時はホームへ戻れる。営業終了は「今日の営業を終了」で販売本数・売上を表示し、当日のJSONと全件CSVを一緒に出力する。2ファイルの保存を確認してホームへ戻る。

保留保存だけでは売上に含めません。保存結果が不明なら同じ注文・操作を照合し、別注文としての再入力や二度の入金・返金を求めません。

## 4. 機能要件

| ID | 機能 | 要件 |
|---|---|---|
| FR-01 | 商品・数量 | 商品ごとの本数を入力する。未入金なら現金未受領を確認して保留を取り消し、当時の価格と数量を下書きへ戻して修正できる |
| FR-02 | 合計金額 | 商品別単価とセット条件から最安額を計算し、本数・内訳・合計を表示する |
| FR-03 | お釣り | お預かり金額から計算し、不足金額での確定を拒否する |
| FR-04 | 会計確定 | 入金の準備を保存した後に確定し、保存成功後に会計済みと表示する。二重登録を防ぐ |
| FR-05 | 注文確認 | 同じPCの会計画面に未受け渡し注文を表示する |
| FR-06 | 注文表示 | 札番号・商品名・商品ごとの本数を表示する。削除済み商品も当時の名前で示す |
| FR-07 | 受け渡し | 商品受け渡しと札回収を一括保存し、待ち一覧から外す。直前の完了は、札が次の注文に一度も再利用されていなければ元に戻せる |
| FR-08 | 番号札 | 空き札を一つの注文へ割り当て、回収後に再利用する。使用中の重複と古い注文からの札操作を拒否する。札枚数は1〜100で変更できる |
| FR-09 | 商品・価格設定 | 商品の追加・削除・商品別価格・セット条件を設定する。未保存の入力を、設定項目や画面の往復で保持する。未保存時は離脱・再読み込み前に確認し、アプリ更新を止める。再読み込み後の未保存入力の復元は対象外。価格・在庫・札枚数・セット・経費は共通の整数入力を使い、空欄と0を区別する |
| FR-10 | 注文履歴 | 現在の営業日の履歴を表示し、札番号・時間帯・状態による絞り込み、時刻・会計額の並べ替え、50件ごとのページ切り替えに対応する。行クリック・会計番号のEnterで詳細を開き、返金操作とは分ける。札番号では並べ替えない |
| FR-11 | 操作の保護 | 設定・全額返金・復元を会計入力から分け、対象と保存内容を確認できるようにする |
| FR-12 | 開催回・営業日 | 営業名を日ごとに登録・変更できる。元の注文と台帳の識別は保持する。別の日の準備・再開は途中の会計・未解決操作・未回収札がない場合に限り、前日の記録は保持する |
| FR-13 | 出力・復元 | 通信なしで設定から復元用JSON、注文履歴から表示条件に合う全ページ分のCSVを出力できる。復元時は内容・整合性・プレビュー後の変更を検証する。保存ファイルの再選択や事前バックアップを必須にしない |
| FR-14 | 値下げ | 商品別の値下げ価格へ手動でまとめて切り替え、次の注文から使う |
| FR-15 | 経費 | 当日の経費合計を登録し、未登録と0円を区別する。経費は営業後の集計画面で登録する |
| FR-16 | 全額返金 | 返金理由と準備を先に保存し、現金確認後に元注文へ関連付けて記録する。売上と販売本数から差し引き、元会計と操作履歴を残す |

未受け渡し本数は調理済み・包装済みも含み、これから焼くべき本数とは区別します。通常の完了操作は、実物の札を回収してから行います。札の紛失・部分受け渡しは現場で別途扱いを決めます。

設定はタブを使わず「商品・価格・在庫」「バックアップ」「番号札」「記録の保護」を縦に並べます。札枚数・記録の保護は開閉せずに表示し、日常語で案内します。

記録の保護は営業記録の作成後と既存記録の起動時に自動で確認・要求し、手動の設定ボタンは置きません。ブラウザが許可しない場合や非対応の場合も会計は継続でき、設定画面に結果とバックアップの案内を表示します。

## 5. 保存・集計の契約

### 注文と操作

- 再利用しない注文IDと、再利用する札番号を分ける。札の現在の所有者は注文ID・割り当てIDで検証する。
- 注文・札・操作結果・連番ログを同じトランザクションで記録する。保存完了前に会計済み・札が空いたと表示しない。
- 同じ操作ID・同じ内容の再試行は既存結果を返す。同じIDで異なる内容は拒否する。
- 全更新でDB識別子と復元世代を確認し、復元前の画面・保留からの古い操作を拒否する。
- 完了取り消しも注文・札・操作・ログを一括保存する。札が再利用された後に空きへ戻っていても、過去の完了取り消しは拒否する。
- 取消や取り消しは記録として残す。確定済みの会計・価格履歴・業務ログを通常操作で削除しない。

### 売上と利益

売上は注文に保存した会計額から実際の返金額を差し引きます。販売本数はセットも本数で数え、全額取消した注文は本数からも差し引きます。現在の価格で過去の注文を再計算しません。

利益は「当日の返金差引後の売上 − 当日の経費合計」です。経費は費目別の明細ではなく合計額を登録し、増えた場合は合計を更新します。未登録は`null`、登録済み0円は`0`として区別し、経費が未登録なら利益も未登録とします。

売上・利益は営業後の専用集計画面で表示し、注文履歴には表示しません。集計画面には、営業日ごとに営業時間10:00〜17:00を横軸とする30分単位の売上棒グラフと、商品別販売本数の円グラフを表示します。返金は元の会計時刻の売上から差し引き、返品分は販売本数から除きます。

## 6. オフラインと復旧

- 同じURL・ブラウザの通常プロファイルを使う。プライベートモードや複数タブでの同時会計は対象外。
- アプリ本体・画像などを事前取得し、営業中に外部API・フォント・CDNを必要としない。
- 初回準備と営業再開を分ける。DBがない状態を自動初期化せず、ホームから明示的に営業を準備する。保存済みの場合は営業名・日付と途中会計・未解決操作を確認する。
- 保留や結果未確認の操作は再起動後に照合できる。現金の受領・返金・実物の札を自動推定しない。
- JSONは全ストアの同じ時点の記録から当日分だけを取り出す。前日の記録はアプリ内にも残す。ダウンロード開始と、ファイル確認・別媒体への退避を区別する。
- 復元時は形式・注文・価格・札・操作・ログを検証する。プレビュー後に記録が変わっていないことを検証し、全データと新世代を原子的に反映する。途中失敗なら元の状態を保つ。
- 既存バックアップと旧形式の価格を読み込める。CSVは集計用とし、完全復元には使わない。
- アプリ更新は利用者が明示的に実行する。入力中・保留・未保存設定や経費があれば止め、更新のためのバックアップ再読込は求めない。

ブラウザデータの削除やPC故障で記録が失われる可能性があります。永続ストレージの要求や`strict`な書き込み指定だけでは、停電・媒体故障への耐久性を保証しません。

## 7. 非機能要件と受入条件

| ID | 分類 | 要件 |
|---|---|---|
| NFR-01 | 操作性 | 会計と待ち一覧を同時に確認し、別注文の受け渡しで入力中の注文を変えない |
| NFR-02 | 対応環境 | 使用するPC・ブラウザを明示し、実機で準備・保存・復旧を検証する |
| NFR-03 | 保守性 | 画面・業務ルール・アプリケーション・保存を分け、依存を内側へ向ける |
| NFR-04 | 運用性 | 開発者不在で営業前確認・閉店・バックアップ・復元を行える |
| NFR-05 | 整合性 | 連打・並行実行でも二重売上・札重複を防ぐ |
| NFR-06 | データ保護 | PCとブラウザの利用者を限定し、実際の注文・経費・バックアップを公開リポジトリへ入れない |
| NFR-07 | 継続利用 | 開催回・営業日・当時の商品と価格を保持する |
| NFR-08 | 費用 | 営業中に有料サービスやクラウドDBの使用量枠を必要としない |
| NFR-09 | 業務継続 | 模擬営業で会計と受け渡しの配置・操作を確認する |
| NFR-10 | オフライン | 通信なしで再読み込み・ブラウザ再起動後も営業できる |
| NFR-11 | 復旧 | 保存失敗・更新・PC変更時にバックアップと照合から復帰できる |
| NFR-12 | 業務ログ | 会計・取消・受け渡し・完了取り消し・設定変更を追記型の記録へ残す |
| NFR-13 | 保存完了 | 関連データを一括保存し、コミット済みの状態を表示する |
| NFR-14 | 耐久性 | 明示した異常終了・再起動の試験条件で、保存完了記録の欠落0を採用基準とする。未試験の条件を明記する |
| NFR-15 | 結果照合 | 保存成功・失敗・結果不明を区別し、同じIDで照合できる |
| NFR-16 | 復元整合性 | プレビュー後の変更を検出し、全ストアと世代を一括で置き換える |
| NFR-17 | 保存時検証 | 画面の操作抑止だけに頼らず、ID・価格・金額・札の所有者・状態を保存時に検証する |
| NFR-18 | 再開時保護 | DB消失を自動初期化せず、保存状態を確認して再開する |

操作部品は共通化し、標準の高さを40px、フォーカス枠を一つにします。アイコンだけの操作にも名前を付け、キーボードで選択欄やダイアログを操作できるようにします。

画面の文字サイズは12px・16px・24pxの3種類に統一します。繰り返し表示する操作は意味が分かるアイコンを優先し、会計・返金・札回収の判断に必要な文字は残します。

受け渡し完了の直後に次の札が同じ操作位置へ移動しないようにし、二度押しで別の注文を完了させません。履歴と返金では会計番号・日時・預かり金・お釣りを確認でき、再利用する札だけを注文の識別に使いません。

1280×640pxのPC画面でも、合計と会計の主操作を確認できる配置にします。注文をクリアしても、新しい入力を始める前なら元に戻せます。

## 8. 本番前に決めること

| 項目 | 確認内容 |
|---|---|
| 端末と担当 | PC・ブラウザ・準備確認担当・会計と受け渡しの操作担当 |
| 営業条件 | 営業時間・販売予定本数・焼き置きや包装・会計場所 |
| 札 | 枚数・満札・紛失・部分受け渡しの扱い |
| 現金 | 取消・返金の現場判断、現金以外の支払いの要否 |
| 経費 | 実際の費目を集計する担当と更新のタイミング |
| バックアップ | 出力頻度・別媒体・保管担当・PC引き継ぎ時の確認方法 |
| 障害 | 許容できる記録損失・紙営業の可否・保存失敗時に営業を止める手順 |

自動試験とは別に、実担当者による模擬営業と、本番PCでのオフライン起動・異常終了・別媒体からの復元を行います。注文件数は未確定のため、1,000件・3,000件は照合用の仮条件です。販売予測や性能の合否基準には使いません。

## 9. 日別の操作と表示

- 新しい営業日は商品・価格・札枚数を引き継いで編集する。在庫はその日ごとに任意登録し、値下げを解除する。保存済みの日は同じ準備画面の「保存済みの営業日」から再開する。
- 表示する残数は当日の用意した合計本数から入金済み本数を引く。追加で注文できる本数は、さらに会計中の予約本数を引いて求める。返金では戻さず、追加・廃棄は合計の直接修正で反映する。残り20本以下は赤で表示し、登録在庫を超える注文と販売・予約本数未満の在庫登録を拒否する。旧データの不整合で残数が負になっている場合は、0本と在庫の確認案内を表示する。
- 商品を上から1〜9キーで1本ずつ追加する。入力欄編集中・別画面・ダイアログ・長押しでは動作しない。Enterは会計・お釣り・確定・札確認の各段階で一度ずつ進める。
- 渡す札は最小の空き番号を仮確保し、「会計を確定」で開く札確認ダイアログで変更できる。会計確定前の番号変更は原子的に保存する。使用中の札へ変更せず、変更失敗でも入力と再試行情報を保持する。
- 札回収で完了した注文は一覧から消す。「回収取消」は下部の固定位置に置き、平均待ちの位置を動かさない。未受け渡し本数は商品別合計で示し、件数バッジ・札検索・完了行を待ち欄へ置かない。
- 札の「経過○分」は会計確定から現在までの時間を30秒ごとに更新する。「平均待ち」は当日の回収済み直近10件から計算する。1件から表示し、実績がなければ「記録なし」とする。予測待ち時間ではない。日別集計はその日全件の実績平均をログから再計算する。
- 履歴は現在の営業日だけを対象とし、時間帯は日本時間10:00〜17:00の30分単位で選ぶ。開始時刻を含み終了時刻を含まない。営業時間外は「すべての時間」で確認する。
- 集計は当日分を初期表示する。同じ台帳で作成した異なる日付のJSONを複数選ぶと日別・合計を計算する。会計用DBを書き換えず、重複日付は拒否する。円グラフは金額の按分でなく販売本数の割合を示す。
- 営業終了時は当日の`yyyy-mm-dd-yakitori.json`と`yyyy-mm-dd-yakitori.csv`を同じSnapshotから出力する。設定・ホームのバックアップはJSONのみ、履歴CSVは表示条件に合う全ページ分とする。
- 終了前に途中会計・未保存編集・未回収札を解消する。ダウンロード開始と保存確認を区別し、最新連番のファイルを確認後に終了する。17時以降は最新記録の保存確認がなければ案内する。ブラウザ終了時に勝手にダウンロードしない。
- ホーム往復で本数・お預かり金額・未保存設定や経費を保持する。再読み込み後に本数の下書きを一時復元するのは、同じDB・世代・営業日に限る。保存済みの会計と二重に復元しない。
- 保存容量の90%以上で警告し、会計入力・未保存編集・保存中には割り込まない。同じ不足状態で繰り返さず、85%未満へ回復後に再通知可能とする。使用量と上限は概算として表示する。
- 日別復元は対象日の記録を戻し、他の日の注文・在庫・経費・会計番号を保持する。会計番号衝突・他の日の未解決作業・プレビュー後変更は拒否する。旧複数日ファイルは含まれる日を復元する。

## 受入条件

自動試験は架空データと専用DBで行います。本番PCの耐久性や実担当者の確認は別に行います。コマンドは[CONTRIBUTING](../CONTRIBUTING.md)を参照してください。

単体試験にはVitest・fake-indexeddbを使います。ブラウザ試験では、ビルドしたPWAをPlaywright付属のChromiumで開きます。専用ポート4273と架空データだけを使い、利用者の本番DBは初期化・更新しません。

オフライン試験はService Workerの準備完了後に記録を読み込み、再読み込みしてから通信を切ります。二重起動の試験は2画面を使い、操作権がない側を止めます。履歴・配置だけでなく、実IndexedDBの保存・再起動も試験します。

在庫の追加・廃棄の差分を記録する旧`adjustStock`も、互換性試験に残します。現在の画面では在庫数を直接入力し、調整ダイアログは設けていません。

### CI・公開で確認すること

GitHub Actionsは型・単体試験・整形・ビルド・ブラウザ試験に成功した成果物だけを公開します。PRでは検証だけを行い、`main`へのpushまたは`main`上の手動実行では公開も行います。公開直前に最新の`main`との一致を確認し、古い実行を公開しません。

公開後はHTMLが最新のJS・CSSを指し、配信内容が検証済みビルドと一致することを確認します。設定と手順は[公開と更新](deployment.md)を参照してください。

### 本番PCで確認すること（自動試験の範囲外）

- [ ] OS・機種・ブラウザ・バージョンと使用URLを記録する。
- [ ] オンライン準備後、通信なしでブラウザを閉じ、同じURLから起動する。
- [ ] 保存完了後の終了・再起動で件数・金額・注文・札・ログが一致することを確認する。
- [ ] 確定直前・直後や保留保存後の強制終了から、二重入金せず照合して復帰する。
- [ ] 容量不足・復元中停止で、元の状態か完全な復元状態のいずれかを保持する。
- [ ] 停電・OS異常終了は条件を記録して検証する。対象条件で保存完了記録の欠落0を採用基準とし、未試験条件を残す。
- [ ] 1,000件・3,000件は照合用の仮条件として保存・出力・復元を確認する。販売予測や全端末の速度保証には使わない。
- [ ] JSONとCSVの両方を保存できること、複数ダウンロードの確認、別媒体への退避と別ブラウザでのJSON復元を確認する。
- [ ] 実担当者が開発者の操作なしで、準備・会計・修正・札回収・取消・設定・履歴・返金・閉店・集計・復元を行う。
- [ ] 営業時間・販売予定・満札・紛失・部分受け渡し・紙営業・許容損失・バックアップ担当と保管先を責任者と決める。

`strict`なIndexedDB書き込みや記録保護の要求は、PC故障・停電・手動削除への無条件の保証ではありません。性能測定の条件と限界は[バックエンドの性能測定](backend.md#性能測定)を参照してください。
