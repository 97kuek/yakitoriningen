# 焼き鳥人間 会計システム 要件定義書

作成日・更新日：2026-10-27

状態：初稿。基本の技術方針は合意済み。販売担当者への確認後に業務仕様を確定する。

## 1. 目的

WASAが早稲田祭に出店する焼き鳥屋「焼き鳥人間」で、注文受付・現金会計・厨房への伝達・商品受け渡しの滞りを減らし、多くのお客さんに対応できるようにする。

開発者が当日現場にいなくても担当者が使え、翌年以降の出店にも引き継げるシステムを目指す。

## 2. 前提と制約

| 項目 | 内容 |
|---|---|
| 開催 | 早稲田祭の2日間。営業時間は確認待ち |
| 出店場所 | 屋外。混雑により通信が不安定になる可能性を見込む |
| 利用端末 | PC・スマホ。OS、機種、台数は未定 |
| 利用方法 | ブラウザからアクセスするWebアプリ |
| ネットワーク | テザリングなどを検討。専用ルーターや現地サーバーを前提にしない |
| 現場の技術対応 | 開発者の立ち会い、Docker、コマンド操作を必要としない運用を目指す |
| 費用 | 有料サービスの利用を避け、無料プランの範囲で運用できるか検証する |
| 過去の実績 | 出店経験はあるが、注文件数などの過去データはない |
| 規模 | 注文件数、販売予定本数、ピーク時の注文量、会計担当人数は確認待ち |

本書では「確認済み」を会話で示された要望・合意事項、「提案」を担当者への確認が必要な仕様候補として扱う。技術方針への合意によって、すべての業務仕様が確定したとは扱わない。

## 3. 利用者

| 利用者 | 役割 |
|---|---|
| 会計担当 | 商品・数量の入力、合計とお釣りの確認、入金確認後の会計確定 |
| 厨房・受け渡し担当 | 会計済みの注文内容と注文状況の確認 |
| 管理担当（提案） | 商品・価格の設定、開催回の管理、売上・履歴の確認、データ出力 |

管理機能を使う人と、役割ごとの操作権限は詳細設計で確定する。

## 4. 業務フロー

1. お客さんが会計担当に注文を伝える。
2. 会計担当が商品と個数を選ぶ。
3. システムが合計金額を表示する。
4. 会計担当がお預かり金額を入力し、システムがお釣りを表示する。
5. 会計担当が入金と釣り銭のやりとりを確認し、会計を確定する。
6. 確定した注文をクラウド経由で厨房・受け渡し側の端末に表示する。

会計確定前の入力内容は、調理対象の注文として厨房に送らない。受け渡し完了の記録、注文番号による照合、会計場所と受け渡し場所の分離は提案段階とする。

## 5. 機能要件

| ID | 機能 | 要件 | 状態 |
|---|---|---|---|
| FR-01 | 商品・数量選択 | 販売商品と個数を選び、会計確定前に修正できる | 確認済み。具体的な商品は確認待ち |
| FR-02 | 合計金額 | 選択した商品・個数に基づく合計を表示する | 確認済み。セット・値引きの計算条件は確認待ち |
| FR-03 | お釣り計算 | お預かり金額からお釣りを自動計算する。不足金額では会計を確定させない | 自動計算は確認済み。不足金額の扱いは設計提案 |
| FR-04 | 会計確定 | 担当者の入金確認後に注文を記録する。連打・再送による二重登録を防ぐ | 入金後の確定は確認済み。重複防止は設計提案 |
| FR-05 | 注文共有 | 通信できる間、会計済み注文を厨房側へ自動反映する | 確認済み |
| FR-06 | 厨房の注文一覧 | 注文内容と個数を確認できる。受付順や種類別の未受け渡し本数の表示を検討する | 注文確認は確認済み。表示内容の詳細は提案 |
| FR-07 | 受け渡し完了 | 渡した注文を待ち一覧から外し、履歴に残す | 提案 |
| FR-08 | 注文の照合 | 注文番号などで、お客さんと注文内容を照合できる | 提案。番号札・注文票の方式は確認待ち |
| FR-09 | 商品設定 | 商品・価格を管理画面から変更し、次回出店でも再利用できる | 提案 |
| FR-10 | 注文履歴・売上集計 | 注文を検索・確認し、売上を集計できる | 要件候補。集計項目、閲覧範囲、取消・返金の反映方法は確認待ち |
| FR-11 | 認証・権限 | スタッフを認証し、担当に応じて閲覧・操作を制限する | 技術方針として採用。認証方法と権限は詳細設計で確定 |
| FR-12 | 開催回の管理 | 開催回ごとに商品設定と注文を分け、過去の記録を保持する | 提案 |
| FR-13 | データ出力 | 会計集計用と復元用のデータを出力できるようにする | 提案。形式・実行者・保存先は確認待ち |

厨房に表示する「未受け渡し本数」は、調理済みの商品も含み得る。「これから焼く必要がある本数」とは区別し、焼き置きや調理済み在庫の運用を確認してから表示を決める。

## 6. 通信断への対応

### 6.1 基本方針

商品選択・お釣り計算は端末内で行い、操作のたびに通信完了を待たせない。営業前にログインし、画面と商品情報を取得して使用端末を準備する。

PWAのキャッシュで画面を、Firestoreの永続キャッシュで取得済みデータと送信待ちの書き込みを保持する構成を検証する。未準備の端末での初回起動や再ログインは、オフライン動作の保証対象に含めない。

| 状況 | 目指す動作 |
|---|---|
| 通信可能 | 注文を保存し、厨房側に反映する |
| 会計端末の通信断 | 準備済みの商品情報で会計を記録し、端末に送信待ちとして保持する |
| 厨房端末の通信断 | 受信済みの注文を表示し、情報が最新ではないことを知らせる |
| 通信復旧 | 送信待ちの同期と注文一覧の再取得を行い、失敗や要確認の注文を表示する |

### 6.2 制約と確認事項

新しい注文の端末間共有には、双方がクラウドと通信できる必要がある。会計端末への保存だけでは、通信断中の厨房への伝達は継続できない。

「端末内の送信待ち」と「クラウド保存済み」を区別する。厨房端末での受信確認を表示する場合は、確認応答を別途設計し、クラウド保存完了を厨房への到達と扱わない。

番号付きの注文票などで厨房に伝える代替運用は提案段階である。通信復旧後に紙と画面の注文を二重に調理・受け渡ししない照合方法も含め、本番前に担当者と決める。

端末内の未同期データはバックアップではない。端末故障やブラウザデータ削除による損失への対応、営業中の同期確認、営業後の保存確認を運用として具体化する。

## 7. 非機能要件

| ID | 分類 | 要件・確認方針 |
|---|---|---|
| NFR-01 | 操作性 | 会計・厨房の画面を担当別に分け、混雑時の入力・確認・操作回数を減らす |
| NFR-02 | 対応環境 | PC・スマホのブラウザで使用する。対応ブラウザを明示し、永続保存・再起動・再同期を実機で確認する |
| NFR-03 | 保守性 | 画面、金額計算などの業務処理、DBアクセスを分離する。商品変更で影響する範囲を限定する |
| NFR-04 | 運用性 | 開発者不在で起動・ログイン・営業前確認・終了確認ができる手順を整える |
| NFR-05 | データ整合性 | 注文IDを再送時も固定し、会計記録と受け渡し状態の更新範囲を分ける |
| NFR-06 | セキュリティ | サーバー側で権限と保存データを検証する。ブラウザの金額や状態を無条件に信頼しない |
| NFR-07 | 継続利用 | 開催回と当時の商品名・単価を保持し、設定変更で過去の売上が変わらないようにする |
| NFR-08 | 費用 | 無料枠への収まり方と余裕を検証し、超過による利用制限を見込んだ運用を決める |
| NFR-09 | 性能 | 模擬営業で会計所要時間、厨房への反映時間、受け渡しまでの時間を確認する。数値目標は営業条件の確認後に決める |
| NFR-10 | データ保全 | 出力・保存・復元の方法を決める。実際の注文データや認証情報を公開リポジトリに入れない |

永続キャッシュが使えない端末で、保存できたように見せて営業を開始しない。利用可能な環境か確認する手順と、利用不可の場合の案内を設計する。

## 8. 技術方針

| 部分 | 採用方針 |
|---|---|
| フロントエンド | React＋TypeScript＋Vite |
| 画面のオフライン対応 | PWA・Service Workerによるキャッシュ |
| 公開先 | Firebase Hosting。サービス提供のURLを使用 |
| データ保存・リアルタイム共有 | Cloud Firestore Standard edition |
| 端末内保存・復旧後の同期 | Firestore Web SDKの永続キャッシュを明示的に有効化 |
| 認証 | Firebase Authentication |
| サーバー側の検証・アクセス制御 | Firestore Security Rules |
| 料金プラン | Firebase Spark |

フロントエンドとバックエンドの責務は分け、初期構成ではバックエンド機能をFirebaseに任せる。Goなどの独自APIサーバーは設けない。Dockerを現場の利用者に導入してもらう運用も採らない。

商品・セット・値引きの仕様が決まった段階で、必要な金額検証をSecurity Rulesで無理なく表現できるか確認する。扱えない場合は独自APIなどを含めて構成を再検討する。Cloud Functions for FirebaseはBlazeプランが必要なため、現在の無料プラン案には含めない。

オフラインの注文記録を、サーバーとの通信が必要な連番発行や厳密な在庫引き当てに依存させない。Firestoreのトランザクションがオフラインでは失敗する制約を踏まえて詳細設計する。

## 9. 規模と無料枠の検証

実際の注文件数は未確定であり、過去の出店実績からは見積もれない。1日1,000件・3,000件などを検証用の仮の規模として置き、営業時間・レジ台数・販売予定本数が分かり次第更新する。この数字は販売予測や合意済みの性能要件ではない。

2026-10-27に確認したFirestore Standard editionの無料枠は次のとおり。

| 項目 | 無料枠 |
|---|---|
| 保存量 | 1 GiB |
| ドキュメント読み取り | 1日50,000回 |
| ドキュメント書き込み | 1日20,000回 |
| 外向きデータ転送 | 月10 GiB |

注文1件あたりの保存、各端末への配信、受け渡し更新、履歴表示、ルールの検証に伴う読み取り、再接続を含めて利用量を見積もる。厨房では未受け渡し注文を中心に取得し、過去の全注文を繰り返し取得しない。

Firestoreの日次枠は太平洋時間の午前0時ごろにリセットされる。日本の営業日ごとの件数だけで無料枠への収まり方を判断しない。Firebase Hostingの転送量など、DB以外の無料枠も本番前に確認する。

無料枠で本番利用できるかは検証後に判断する。利用制限に達する可能性が高い場合は、機能・構成・運用を見直す。有料プランへの切り替えは自動的に決めず、別途相談する。

| ID | 確認事項 | 影響する設計 |
|---|---|---|
| Q-01 | 商品、単価、セット販売、値引き | 会計画面、金額計算、サーバー側の検証 |

## 11. 実装・本番運用までの進め方

1. 担当者の回答を反映し、初期版の機能範囲と提案部分を確定する。
2. 金額や保存データの検証を無料プラン内で扱えるか確認する。
3. 対応ブラウザ、通信断時の代替運用、データの保存・復元手順を決める。
4. 通信断、再読み込み、再起動、復旧後の同期、連打、権限違反、保存拒否の動作を検証する。
5. 仮の注文量と端末台数で無料枠の利用量を見積もり、模擬営業で処理の滞りを確認する。
6. 開発者がいない状況で、担当者が営業前の準備と営業後の確認を行えるか確認する。
