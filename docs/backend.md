# バックエンド相当の処理

会計の業務処理とDB保存は、使用するPCのブラウザ内で実行します。サーバー側のバックエンドはありません。Cloudflare Pagesはアプリ本体を配信するだけで、注文は保存しません。

## 責務と主要ファイル

| 層・ファイル | 責務 |
|---|---|
| `src/domain/model.ts` | 注文・価格・操作・DB世代などの型と入力制約 |
| `src/domain/constants.ts`、`time.ts` | 上限値・初期値・営業時間・時間帯の長さ、日本時間の扱い |
| `src/domain/catalog.ts`、`pricing.ts` | 商品の取得、通常・値下げ価格、旧形式の価格、最安のセット計算 |
| `src/domain/order.ts`、`ticket.ts`、`handoff.ts` | 注文の状態遷移、札の割り当て・解放、札再利用後の完了取り消しの拒否 |
| `src/domain/history.ts`、`snapshot.ts` | 履歴の絞り込み・並べ替え、保留中の会計と確認が必要な操作の抽出 |
| `src/domain/sales.ts` | 売上・返金・本数・利益の集計 |
| `src/application/ports.ts` | 画面向け`Cashier`、保存向け`LedgerRepository`の契約 |
| `src/application/cashier-commands.ts` | 操作の準備・実行・破棄・復元、世代と再試行の検証 |
| `src/application/backup.ts`、`order-history.ts` | バックアップの形式・関連記録・操作履歴の整合性検証 |
| `src/storage/database.ts`、`ledger-repository.ts` | DexieのDB定義とトランザクション |
| `src/storage/cashier-store.ts` | 業務処理とIndexedDB・ID生成・時計の接続 |
| `src/bootstrap.ts` | DB、時刻、ID生成、変更購読を接続 |

依存は`application → domain`です。storageがapplicationの保存ポートを実装します。domainはReact・IndexedDB・Dexieを参照せず、applicationもDexieへ依存しません。

## 保存するデータ

| ストア | 内容 |
|---|---|
| `meta` | 開催回・営業日・適用価格・札枚数・経費合計・DB識別子・世代・ログ連番 |
| `prices` | 商品と価格設定の履歴 |
| `orders` | 商品名・数量・味別本数・当時の価格と味名・会計額・入金・受け渡し・返金の記録 |
| `tickets` | 札番号と現在の注文・割り当てID |
| `operations` | 操作ID・内容・準備中／完了／破棄・結果 |
| `logs` | 操作IDに対応する追記型の連番ログ |

注文IDは再利用せず、札番号だけを回収後に再利用します。営業日を変えても前日の記録は保持します。

経費合計の`null`は未登録、`0`は登録済み0円です。日別の経費は、各日の最後の完了済み`expense`操作から求めます。既存の`meta.expenseTotal`には、互換性のため直近の登録額を残します。

## 操作のデータフロー

1. 操作IDとDB識別子・世代を付け、実行する内容を準備記録として保存する。
2. 同じ操作IDの既存記録があれば内容を照合する。異なる内容は拒否する。
3. 実行時にDB世代・価格・金額・注文状態・札の所有者を検証する。
4. 注文・札・設定変更・操作結果・連番ログを同一トランザクションで反映する。
5. コミット後に結果を返す。完了済み操作の再試行は既存結果を返す。

受け渡しと札回収は`complete`として一括保存します。`undoHandoff`は対象の完了操作を参照し、札が次の注文へ割り当てられる前だけ待ちへ戻せます。一度再利用された札は、その後空いていても古い完了を取り消せません。

注文を変更しても、元の数量や価格は上書きしません。未入金なら取消記録を保存して下書きへ戻し、入金後なら全額返金の記録を残します。部分返金は対象外です。

## バックアップ・復元

JSONの出力では全ストアを同じ時点で取得し、`dailySnapshot`で営業日1日分に絞ります。当日の注文に必要な全操作、当日の設定操作、必要な価格版と札を保存します。別の日の注文はファイルに含めません。

ログ連番は会計番号にも使うため詰め直さず、省略数を任意項目の`meta.omittedLogs`へ記録します。旧ファイルは省略0件として従来の連続性を検証します。読み込み時には型・価格計算・注文と札・操作結果・ログ順・受け渡し履歴を照合します。経費欄や商品別価格欄がない旧JSON形式も、互換処理で受け付けます。

復元前にはファイルの内容確認を求めます。プレビュー時点のDBを比較対象として保持し、その後に記録が変われば復元を拒否します。バックアップの出力や、出力したファイルの再選択は必須にしません。成功時には全データと新しい復元世代を一括反映し、復元前の操作は再実行できなくなります。

復元の対象は、ファイルに含まれる営業日の注文と設定です。別の日の注文・在庫・経費・会計番号は保持します。独立した記録の会計番号が衝突する場合や、別の日に途中の会計・未回収札がある場合は、元の記録を変更せずに復元を拒否します。複数日を含む旧バックアップは、その日数分をまとめて復元します。集計のために読み込む場合は、集計画面を使います。

CSVは集計用で、完全復元には使えません。会計状態・受け渡し・札回収は日本語で出力し、営業日と日本時間の注文時刻を秒まで含めます。

### 営業日の準備と再開

別の日の営業は`startDay`で準備します。準備時の連番と一致すること、未解決操作・使用中の札がないこと、対象日が新しいことを確認します。そのうえで、営業日・価格・札枚数・任意の在庫を一つのトランザクションで保存します。以前の注文・操作・価格は残し、破棄済みの準備は日付の重複とみなしません。

`catalog`は商品・価格・当日の在庫を同時に保存します。初回の`initialize`も任意の設定を同じトランザクションで作り、`startDay`の完了記録に札枚数も残します。旧形式で初日の札枚数が未記録の場合は、別の日を準備する直前に`tickets`の完了記録を補います。

保存済みの日は`resumeDay`で商品・札枚数を再開し、在庫・経費はその日のログから取得します。

日付を変えた後は、古い注文作成・設定操作を別の日へ適用することを拒否します。元の日付へ戻して再試行するか、確認待ちの操作を破棄します。経費のメタ情報には旧形式との互換性のため最後の登録額を残し、画面に表示する経費は日別の操作から計算します。

## 変更手順

1. [要件](requirements.md)に業務上の振る舞いを定め、domainに計算・状態のルールを置く。
2. applicationで検証とトランザクション内の保存手順を実装する。ID・時刻・保存先は引数またはポートから受け取る。
3. 保存形式を変える場合は既存DB・JSONとの互換性、復元検証、過去注文の集計・CSVへの影響を確認する。関数名だけを整理する場合は保存済みコマンド文字列を変えない。
4. 二重実行・古い世代・札再利用・途中の書き込み失敗を試験し、全体が反映されるか、全体が戻ることを確認する。
5. 実際の営業データを使わず、架空データと専用DBで検証する。コマンドは[CONTRIBUTING.md](../CONTRIBUTING.md)を参照する。

## 日別在庫・集計

在庫は`stock`（旧形式）・`catalog`・`startDay`操作に、商品ごとの用意した本数を記録します。過去の`adjustStock`は商品IDと追加・廃棄の差分として読み込み・照合しますが、現在のUIでは合計本数を直接入力します。

残数は日別の完了ログを連番順に適用した在庫から、`paidAt`のある当日の注文の本数を差し引いて求めます。返金済みの注文も差し引き、新しいストアの追加や既存商品の書き換えは行いません。在庫未登録の商品には残数を表示しません。

集計用のファイルも通常のバックアップ検証を通し、各ファイルから営業日分のデータを取り出します。複数ファイルを読み込む場合は、同じ開催回で日付が異なるものだけを許可します。集計中のデータは画面内だけに置き、DBへの復元や書き込みは行いません。

日別バックアップには札ごとの`reuseSequence`を残します。これにより、別の日に札を再利用した後や、札枚数を増やして番号を再発行した後に、過去の受け渡しを取り消すことを防ぎます。

予約作成時にもトランザクション内で在庫の上限を検証し、会計中の予約本数を確保済みとして差し引きます。返金しても在庫は戻しません。

平均待ち時間は会計確定時刻と札回収ログから求め、集計のためだけに平均を記録するログは作りません。

札ごとの経過分数は、`domain/wait-time.ts`の`elapsedWait`へ表示用の現在時刻を渡して計算します。会計確定時刻から数え、回収済みの注文・予約・不正な日時を除外します。平均待ちの実績とは別の値として、画面で30秒ごとに再計算します。

### 手動の札選択とバックアップ案内

`reserve`の任意項目`ticket`に希望番号を保存します。番号を指定していない旧操作では、空き札の最小番号を選びます。指定番号が使用中・範囲外なら、別番号へ変更せずに拒否します。保存時にも同じトランザクション内で所有権を確認します。バックアップの検証では、最新の`selectTicket`操作と注文の札が一致することを確認し、その操作がなければ`reserve`の指定札と照合します。

`BackupHistory`は、利用者がファイルの保存を確認した時点の連番を保存するUI用ポートです。`LocalBackupHistory`はDB識別子・復元世代・営業日で記録を分け、`localStorage`が使えなければメモリ内で動作します。売上・注文・札のDBとは分離しています。この記録は物理ファイルの保存完了を意味せず、ダウンロードを開始しただけでは確認済みにしません。

`selectTicket`は未確定注文だけに適用し、変更元の`from`と変更先の`ticket`を記録します。新しい札の空きと旧札の所有権を検証し、旧札の解放・新札の確保・注文・操作・連番ログを同じトランザクションで保存します。入金確認の操作IDと金額、割り当てIDは保ちます。

札再利用の連番を更新し、同じ操作IDで再試行した場合は既存の結果を返します。会計確定後の変更、使用中の札への変更、変更元が違う古い操作は拒否します。完了取消の履歴を再生する際は、各操作の時点までの割り当てだけで判定します。後の札変更を過去の再利用と誤認しません。

`DraftCache`は営業記録とは独立した一時入力のポートです。`LocalDraftCache`は入力形式を検証し、営業日・DB・復元世代が異なる入力は復元しません。注文が空になったら一時保存を削除します。一時保存できない環境でも、離脱前の確認は維持します。

## 在庫と価格の計算

`stockLevels`は販売本数を差し引いた在庫、表示用の残数、予約を除いた注文可能数を一度に求めます。`Checkout`ではSnapshotが変わったときだけ再計算し、本数の入力だけでは在庫履歴を集計し直しません。

`quote`のセット計算は、価格ごとの数量を使います。商品1本ごとの単価を配列へ展開しません。組合せ自由のセットでは、価格の高い順に節約額を計算します。組合せ自由のセットと旧形式の種類別セットの両方に対応し、最安額の計算と保存形式は維持します。

## 履歴検証の負荷

`validateSnapshot`は完了済み操作を注文ごとに分類し、ログ連番も一度だけMapへまとめます。各注文の履歴を再生する検証では、この分類とMapを共有し、全件を繰り返し検索する負荷を減らします。保存形式・検証項目・旧`reserve`の札復元は変更しません。測定条件と結果は末尾に記載します。

## 営業名の扱い

営業名の表示は`domain/day.ts`の`dayName`に集約します。`startDay`の任意項目`name`と`renameDay`の`name`を完了ログの連番順にたどり、指定日の最新名を返します。旧データでは`meta.event`を表示します。名前の前後の空白は除き、空欄と上限超過を拒否します。

`meta.event`は既存の台帳グループの識別に残し、改名しても注文・操作に保存された`event`は上書きしません。`renameDay`の操作とログは同じトランザクションで追記します。日付を変えた後は、古い改名操作を別の日へ適用しません。

日別JSONには必要な改名操作を残し、復元・再開・CSVでも同じ日別名を使います。CSVの名前は日ごとに一度だけ解決します。同じ台帳から保存した異なる日付のバックアップなら、日別の表示名が違っていても集計できます。独立した別台帳の統合は対象外です。

## 味別の注文

`Price.flavors`は味のIDと名前の配列、`Order.flavors`と`reserve.flavors`は商品ID→味ID→本数のマップです。いずれも任意項目とし、旧記録を読み込む際に追加しません。味名は注文内の価格版から表示するため、改名や削除後も当時の注文を保ちます。

`validateFlavorQuantities`は商品・味のIDと本数を、保留保存前と実行時に検証します。味別合計が商品合計を超える値は拒否します。旧注文を修正したときの未指定分を残せるよう、味別合計が商品合計未満の記録も扱います。新規の画面入力は全本数を味に割り当てます。価格・在庫の計算には従来の`quantities`を使います。

バックアップでは、注文と予約操作の味別本数が一致することも検証します。CSVは従来の列順を保ち、末尾の「味別内訳」に商品・味・本数を出力します。味の記録がない旧注文では、この列を空欄にします。


## 性能測定

### 履歴検証（2026-11-02）

架空の会計・札回収済みSnapshotを使い、Node/Vite SSRで履歴検証関数だけを測定しました。1回ウォームアップ後の3回平均です。実ブラウザ・DB保存・描画の応答時間ではありません。

| 注文数 | 操作・ログ数（各） | 索引化前 | 索引化後 |
|---:|---:|---:|---:|
| 1,000 | 3,000 | 356.93ms | 44.46ms |
| 5,000 | 15,000 | 5,122.05ms | 189.35ms |

待ち時間計算は5,000注文で約4ms（30回平均）です。入力だけの変更では再計算せず、集計は遅延読み込み・メモ化しています。

### 在庫・価格計算（2026-11-03）

架空データを使い、Node v26.8.1 / Vite SSRで関数単体の処理時間を比較しました。旧実装と新実装で、価格303条件・在庫7条件の出力が一致することを先に確認しています。各30回のウォームアップ後、旧新の実行順を交互にした9ラウンドの中央値を求めました。表は1呼び出し当たりの時間です。

| 条件 | ラウンドごとの呼び出し数 | 変更前 | 変更後 |
|---|---:|---:|---:|
| 在庫：5,000注文・15,000操作・15,000ログ | 15 | 3.975ms | 1.372ms |
| 価格：通常6本 | 1,000 | 0.00497ms | 0.00456ms |
| 価格：30商品×999本・組合せ自由 | 100 | 1.164ms | 0.0437ms |

在庫は従来の会計画面での3関数呼び出しと、`stockLevels`1回を比較しました。この測定には、メモ化による再計算の省略、実ブラウザの描画、DB保存は含みません。実機の応答時間を保証する値ではなく、対象端末での長時間利用・保存・出力・復元の時間は別途測定します。
