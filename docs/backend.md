# バックエンド相当の処理

このアプリにサーバー側のバックエンドはありません。会計の業務処理とDB保存を、使用するPCのブラウザ内で実行します。Cloudflare Pagesはアプリ本体を配信し、注文を保存するサーバー処理は持ちません。

## 責務と主要ファイル

| 層・ファイル | 責務 |
|---|---|
| `src/domain/model.ts` | 注文・価格・操作・DB世代などの型と入力制約 |
| `src/domain/constants.ts`、`time.ts` | 上限値・初期値・営業時間・時間帯の長さ、日本時間の扱い |
| `src/domain/catalog.ts`、`pricing.ts` | 商品の取得、通常・値下げ価格、旧形式の価格、最安のセット計算 |
| `src/domain/order.ts`、`ticket.ts`、`handoff.ts` | 注文の状態遷移、札の割り当て・解放、札再利用後の完了取り消しの拒否 |
| `src/domain/history.ts`、`snapshot.ts` | 履歴の絞り込み・並べ替え、保留中の会計と確認が必要な操作の抽出 |
| `src/domain/sales.ts` | 売上・返金・本数・利益の集計 |
| `src/application/ports.ts` | 画面向け`Cashier`、保存向け`LedgerRepository`の契約 |
| `src/application/cashier-commands.ts` | 操作の準備・実行・破棄・復元、世代と再試行の検証 |
| `src/application/backup.ts`、`order-history.ts` | バックアップの形式・関連記録・操作履歴の整合性検証 |
| `src/storage/database.ts`、`ledger-repository.ts` | DexieのDB定義とトランザクション |
| `src/storage/cashier-store.ts` | 業務処理をIndexedDB・ID生成・時計へ接続したもの |
| `src/bootstrap.ts` | DB、時刻、ID生成、変更購読を接続 |

依存は`application → domain`です。storageがapplicationの保存ポートを実装します。domainはReact・IndexedDB・Dexieを参照せず、applicationもDexieへ依存しません。

## 保存するデータ

| ストア | 内容 |
|---|---|
| `meta` | 開催回・営業日・適用価格・札枚数・経費合計・DB識別子・世代・ログ連番 |
| `prices` | 商品と価格設定の履歴 |
| `orders` | 商品名・数量・当時の価格・会計額・入金・受け渡し・返金の記録 |
| `tickets` | 札番号と現在の注文・割り当てID |
| `operations` | 操作ID・内容・準備中／完了／破棄・結果 |
| `logs` | 操作IDに対応する追記型の連番ログ |

注文IDは再利用せず、札番号だけを回収後に再利用します。経費合計の`null`は未登録、`0`は登録済み0円です。営業日を変えても、開催回全体の経費や未完了の注文は保持します。

## 操作のデータフロー

1. 操作IDとDB識別子・世代を付け、実行する内容を準備記録として保存する。
2. 同じ操作IDの既存記録があれば内容を照合する。異なる内容は拒否する。
3. 実行時にDB世代・価格・金額・注文状態・札の所有者を検証する。
4. 注文・札・設定変更・操作結果・連番ログを同一トランザクションで反映する。
5. コミット後に結果を返す。完了済み操作の再試行は既存結果を返す。

受け渡しと札回収は`complete`として一括保存します。`undoHandoff`は対象の完了操作を参照し、札が次の注文へ割り当てられる前だけ待ちへ戻せます。一度再利用された札は、その後空いていても古い完了を取り消せません。

注文変更は元の数量や価格を上書きする方式ではありません。未入金なら取消記録を保存して下書きへ戻し、入金後なら全額返金の記録を残します。部分返金は対象外です。

## バックアップ・復元

JSONは全ストアを同じ時点で取得します。読み込み時に型・価格計算・注文と札・操作結果・ログ順・受け渡し履歴を照合します。従来の経費欄や商品別価格欄がないファイルも互換処理で受け付けます。

復元前にはファイルの内容確認を求めます。プレビュー時点のDBを比較対象として保持し、その後に記録が変われば復元を拒否します。バックアップ出力や出力ファイルの再選択は必須にしません。成功時には全データと新しい復元世代を一括反映します。復元前の操作は再実行できません。CSVは集計用で、完全復元には使えません。会計状態・受け渡し・札回収は日本語で出力し、営業日と日本時間の注文時刻（秒まで）を含めます。DBと復元用JSONの形式は変えません。

翌年への切り替えは、未完了の注文・操作と使用中の札がないことを確認してから行います。保存は任意で、切り替え画面を開いた時点からのDB変更は拒否します。新しい開催回には現在の商品・価格と札枚数を引き継ぎ、値下げを解除します。注文・経費・操作履歴は引き継がず、保存した場合は前年ファイルで保管できます。復元と同じ一括置換・世代変更で、途中失敗や確認中の変更から保護します。

## 変更手順

1. [要件](requirements.md)に業務上の振る舞いを定め、domainに計算・状態のルールを置く。
2. applicationで検証とトランザクション内の保存手順を実装する。ID・時刻・保存先は引数またはポートから受け取る。
3. 保存形式を変える場合は既存DB・JSONとの互換性、復元検証、過去注文の集計・CSVへの影響を確認する。関数名だけを整理する場合は保存済みコマンド文字列を変えない。
4. 二重実行・古い世代・札再利用・途中の書き込み失敗を試験し、全体が反映されるか、全体が戻ることを確認する。
5. 実際の営業データを使わず、架空データと専用DBで検証する。コマンドは[CONTRIBUTING.md](../CONTRIBUTING.md)を参照する。
