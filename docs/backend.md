# バックエンド相当の処理

このアプリにサーバー側のバックエンドはありません。会計の業務処理とDB保存を、使用するPCのブラウザ内で実行します。Cloudflare Pagesはアプリ本体を配信し、注文を保存するサーバー処理は持ちません。

## 責務と主要ファイル

| 層・ファイル | 責務 |
|---|---|
| `src/domain/model.ts` | 注文・価格・操作・DB世代などの型と入力制約 |
| `src/domain/constants.ts`、`time.ts` | 上限値・初期値・営業時間・時間帯の長さ、日本時間の扱い |
| `src/domain/catalog.ts`、`pricing.ts` | 商品の取得、通常・値下げ価格、旧形式の価格、最安のセット計算 |
| `src/domain/order.ts`、`ticket.ts`、`handoff.ts` | 注文の状態遷移、札の割り当て・解放、札再利用後の完了取り消しの拒否 |
| `src/domain/history.ts`、`snapshot.ts` | 履歴の絞り込み・並べ替え、保留中の会計と確認が必要な操作の抽出 |
| `src/domain/sales.ts` | 売上・返金・本数・利益の集計 |
| `src/application/ports.ts` | 画面向け`Cashier`、保存向け`LedgerRepository`の契約 |
| `src/application/cashier-commands.ts` | 操作の準備・実行・破棄・復元、世代と再試行の検証 |
| `src/application/backup.ts`、`order-history.ts` | バックアップの形式・関連記録・操作履歴の整合性検証 |
| `src/storage/database.ts`、`ledger-repository.ts` | DexieのDB定義とトランザクション |
| `src/storage/cashier-store.ts` | 業務処理をIndexedDB・ID生成・時計へ接続したもの |
| `src/bootstrap.ts` | DB、時刻、ID生成、変更購読を接続 |

依存は`application → domain`です。storageがapplicationの保存ポートを実装します。domainはReact・IndexedDB・Dexieを参照せず、applicationもDexieへ依存しません。

## 保存するデータ

| ストア | 内容 |
|---|---|
| `meta` | 開催回・営業日・適用価格・札枚数・経費合計・DB識別子・世代・ログ連番 |
| `prices` | 商品と価格設定の履歴 |
| `orders` | 商品名・数量・当時の価格・会計額・入金・受け渡し・返金の記録 |
| `tickets` | 札番号と現在の注文・割り当てID |
| `operations` | 操作ID・内容・準備中／完了／破棄・結果 |
| `logs` | 操作IDに対応する追記型の連番ログ |

注文IDは再利用せず、札番号だけを回収後に再利用します。経費合計の`null`は未登録、`0`は登録済み0円です。日別の経費は各日の最後の完了済みexpense操作から求めます。既存meta.expenseTotalは互換性のため直近の登録額を維持します。営業日を変えても前日の記録を保持します。

## 操作のデータフロー

1. 操作IDとDB識別子・世代を付け、実行する内容を準備記録として保存する。
2. 同じ操作IDの既存記録があれば内容を照合する。異なる内容は拒否する。
3. 実行時にDB世代・価格・金額・注文状態・札の所有者を検証する。
4. 注文・札・設定変更・操作結果・連番ログを同一トランザクションで反映する。
5. コミット後に結果を返す。完了済み操作の再試行は既存結果を返す。

受け渡しと札回収は`complete`として一括保存します。`undoHandoff`は対象の完了操作を参照し、札が次の注文へ割り当てられる前だけ待ちへ戻せます。一度再利用された札は、その後空いていても古い完了を取り消せません。

注文変更は元の数量や価格を上書きする方式ではありません。未入金なら取消記録を保存して下書きへ戻し、入金後なら全額返金の記録を残します。部分返金は対象外です。

## バックアップ・復元

JSONは全ストアを同じ時点で取得した後、dailySnapshotで営業日1日分に絞ります。当日注文に必要な全操作、当日の設定操作、必要な価格版と札を保存します。別日の注文はファイルに含めません。ログ連番は会計番号にも使うため詰め直さず、省略数を任意のmeta.omittedLogsへ記録します。旧ファイルは省略0件として従来の連続性を検証します。読み込み時に型・価格計算・注文と札・操作結果・ログ順・受け渡し履歴を照合します。従来の経費欄や商品別価格欄がないファイルも互換処理で受け付けます。

復元前にはファイルの内容確認を求めます。プレビュー時点のDBを比較対象として保持し、その後に記録が変われば復元を拒否します。バックアップ出力や出力ファイルの再選択は必須にしません。成功時には全データと新しい復元世代を一括反映します。復元前の操作は再実行できません。CSVは集計用で、完全復元には使えません。会計状態・受け渡し・札回収は日本語で出力し、営業日と日本時間の注文時刻（秒まで）を含めます。旧形式の読み込みを維持します。復元はファイルに含まれる営業日の注文と設定を対象にし、別の日の注文・在庫・経費・会計番号は保持します。集計目的では集計画面の読み込みを使用します。独立した記録の会計番号が衝突する場合や、別の日に途中の会計・未回収札がある場合は、元の記録を変更せず拒否します。旧複数日バックアップは含まれる日をまとめて復元します。

別の日の営業は `startDay` で準備します。準備時の連番との一致、未解決操作・使用中の札がないこと、対象日が新しいことを確認し、営業日・価格・札枚数・任意在庫を一つのトランザクションで保存します。以前の注文・操作・価格は残します。破棄済みの準備は日付重複としません。`catalog` は商品・価格・当日の在庫を同時に保存します。初回のinitializeも任意設定を同じトランザクションで作り、startDayの完了記録で札枚数も残します。以前の形式で初日の札枚数が未記録なら、別日を準備する直前にticketsの完了記録を補います。保存済みの日はresumeDayで商品・札枚数を再開し、在庫・経費はその日のログから取得します。

日付を変えた後に古い注文作成・設定操作を別の日へ適用することは拒否します。元の日付へ戻して再試行するか、確認待ちを破棄します。経費メタ情報は旧形式との互換性のため最後の登録額を保持し、画面は日別の操作から計算します。

## 変更手順

1. [要件](requirements.md)に業務上の振る舞いを定め、domainに計算・状態のルールを置く。
2. applicationで検証とトランザクション内の保存手順を実装する。ID・時刻・保存先は引数またはポートから受け取る。
3. 保存形式を変える場合は既存DB・JSONとの互換性、復元検証、過去注文の集計・CSVへの影響を確認する。関数名だけを整理する場合は保存済みコマンド文字列を変えない。
4. 二重実行・古い世代・札再利用・途中の書き込み失敗を試験し、全体が反映されるか、全体が戻ることを確認する。
5. 実際の営業データを使わず、架空データと専用DBで検証する。コマンドは[CONTRIBUTING.md](../CONTRIBUTING.md)を参照する。

## 日別在庫・集計

在庫はstock（旧形式）・catalog・startDay操作に商品別の用意した本数を記録します。adjustStockは商品IDと追加・廃棄の差分を記録します。日別の完了ログを連番順に適用し、paidAtのある当日注文の本数（返金済みを含む）を差し引きます。新しいストアや既存商品の書き換えは行いません。未登録商品は残数を表示しません。

集計用の複数ファイルは通常のバックアップ検証を通し、各ファイルの営業日分を取り出します。同じ開催回・異なる日付だけを許可します。集計中のデータは画面内だけに置き、DBへの復元や書き込みは行いません。

日別バックアップでは札ごとの `reuseSequence` を残します。別日の再利用や札枚数を増やして番号を再発行した後に、過去の受け渡しを取り消すことを防ぎます。

在庫の上限は予約作成時にもトランザクション内で検証し、会計中の予約本数も確保済みとして差し引きます。返金した商品は戻しません。平均待ち時間は会計確定時刻と札回収ログから導き、集計のためだけの重複した平均ログは作りません。

札ごとの経過分数はdomain/wait-time.tsのelapsedWaitへ表示用の現在時刻を渡して計算します。会計確定時刻から数え、回収済み・予約・不正な日時を除外します。平均待ちの実績とは別の値で、画面は30秒ごとに再計算します。
