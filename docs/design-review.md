# 焼き鳥人間 設計レビュー結果

実施日・方針更新日：2026-10-30

現在の採用方針：その後のユーザーの「誰のPCでも気軽に起動したい」という要望を受け、OS別の保存用アプリを採用せず、PWA＋IndexedDBへ一本化する。以下の方式比較はレビュー時の検討記録として残す。保存・復旧の受入条件は弱めず、実機検証を本番利用の条件とする。

対象：[要件定義書](requirements.md)、[アーキテクチャ設計書](architecture.md)、[README](../README.md)

## 1. レビューの目的と範囲

ユーザーの依頼に基づき、DB信頼性、現場運用、設計に反論する批判担当の3エージェントが、同じ資料を独立して点検した。PC1台・営業中はオフライン・無料・開発者不在でも使えることを前提とし、DBへの記録の確実性を最優先とした。PCの処理速度は評価対象に含めていない。

アプリは未実装。ここでの指摘は設計上の不足であり、実装の不具合や性能を測定した結果ではない。主担当は各指摘を現行文書と一次資料に照合し、技術側で修正できる事項とユーザーの運用判断が必要な事項を分けた。

## 3. 批判担当からの反論と判断

「DBを安全にしたい」という要望だけで、PWAをSQLiteへ変更する根拠は足りない。同時に、現行のPWAが必要な保存条件を満たすという実機の証拠もない。レビュー時点ではこの反論を採用し、同じ合格条件で比較した。その後、起動の手軽さを優先するユーザーの要望に合わせてPWAを採用方針とし、保存・復旧の合格条件を実機で確認することにした。

PWAを推す理由は、了承済みの初回オンライン準備とブラウザ利用に沿い、OS別の起動アプリの配布・保守を増やさずに済むこと。SQLiteを推す理由は、保存用アプリがDBファイル・耐久性設定・自動バックアップを一括管理できる場合、ブラウザのプロファイルや保存領域への依存を減らせること。ただし、SQLiteは設定、再試行、バックアップ、起動・復旧手順の検証を省略できる理由にはならない。

Goは保存用アプリの候補であり、DB信頼性のために必ずGoを使うという判断はしない。利益表示、汎用の商品編集、複雑な割引などを先に増やす提案も採らず、初期版の保存・照合・復元を優先する。

## 4. 保証範囲の比較

| 論点 | 案A：PWA＋IndexedDB | 案B：保存用アプリ＋SQLite |
|---|---|---|
| 一部だけ保存される問題 | 同じトランザクションと状態検証で対処 | 同じトランザクションと制約・状態検証で対処 |
| 保存成功後に応答が失われる問題 | 操作IDと結果の照会が必要 | 同じ照会が必要。DB変更だけでは解決しない |
| OS異常終了・停電 | strictの要求と実機確認。無条件の耐久保証ではない | journal・sync設定と実機確認。NORMAL＋WALを耐久性の根拠にしない |
| ブラウザデータ削除 | 保存済み記録も失い得る。確認済みファイルから復元 | DBをブラウザ外に管理すれば、この削除から分離できる |
| PC故障・媒体故障 | 別媒体のバックアップが必要 | 同様。内蔵ディスク内の自動コピーだけでは不十分 |
| 現場・翌年の起動 | 同じブラウザ・URLで準備し検証 | OSに合う配布物と起動・引き継ぎ手順が追加で必要 |

IndexedDBのstrictはブラウザへの耐久性の要求、persistは保存領域の自動削除方針への対策であり、バックアップではない。Dexieのキャッシュ設定によるコミット前反映は、会計の保存完了表示に使わない。

SQLiteではWALと同期設定を明示し、有効値を読み戻す。稼働中にDB本体だけをコピーせず、Backup API等で整合した状態を取得する。どちらの方式も、端末や媒体がすべての同期要求を正しく処理すること、バックアップが実際に退避されていることまでDB名だけでは保証できない。

## 5. 実装前に残る判断

- 保存用アプリの導入可否は、現在の方針では追加導入しないことで解決。使用するPC・対応ブラウザでPWAの準備と保存を確認する。
- ブラウザデータ消去・PC故障時に失ってよい記録の範囲と、復旧まで紙営業を行うか。その条件でバックアップ頻度・保存先・担当を決める。
- 札の紛失・満札・部分受け渡し、部分返金、紙からの復旧入力の最小手順を確認する。

冪等性、整合したバックアップ、復元中断時の原子性は、ユーザーに安全性の選択を委ねず技術側で具体化する。

## 6. 実装後に確認すること

コミット直前・直後・完了表示直前の停止、同じ操作の再試行、札再利用後の古い操作、保存容量不足、並行するバックアップ、復元中断、DB消失、アプリ更新を試験する。アプリ停止とOS異常終了を分けて記録する。

復旧試験では、開発者が操作せず担当者自身に、結果不明の照合・確認済みファイルからの復元を行ってもらう。DBの件数・売上・本数だけでなく、注文、札、業務ログ、操作結果の一致を確認する。

レビューを反映した文書であっても、本番動作を検証済みとは扱わない。保存方式の採否、実装、受入試験、本番利用の可否は別の段階として判断する。
